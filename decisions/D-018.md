# D-018  Two work chats in parallel, Bugs and Evolutions, under one control room

    Scope:       global. Live for control-tower, inherited by every project control room
                 at adoption.
    State:       answered
    Decided by:  Yassir, 2026-09-20
    Supersedes:  nothing. Refines D-016 (streams) and the bus rule "one order in flight
                 per project", which becomes one per chat.

## Context

One chat doing everything serialises bugs behind features. And on 2026-09-20, two chats
working the hub at once collided three ways: a lost write on config.yml, one generated
prompt executed twice, and git lock files left in the repo. Parallel work is wanted, and
unmanaged parallel work has already failed.

## Options

1. **Recommended, and taken.** Two work chats split D-016's Evolutions stream by its
   existing tag: Bugs takes `bug`, Evolutions takes `feature`. The control room is the
   only writer of shared files. Each work chat claims its paths before touching them and
   works in its own clone of the project repo. D-016 is unchanged.
2. Three streams, superseding D-016. A third status row forever, for no extra safety.
3. One chat at a time. Safe, and gives up the parallelism asked for.

## Reversibility

High. Two prompts, two clones, one claims folder. Collapsing back to one chat means
merging two branches and closing two chats.

## Cost of not deciding

Bugs keep waiting behind features, and the next parallel session repeats today's
collisions with nothing to stop them.

## The decision

### Who writes what

| Actor | Writes | Never writes |
|---|---|---|
| Control room | evolution map, status, registry, config, decisions, derogations, release plans, merges into main, commits of `_tower` | code for a story a work chat holds |
| Bugs chat | its clone `AI Control Tower/.chats/bugs`, branch `bugs`; its claims file; its reports; new handover files | any shared file above, `_tower` commits, main |
| Evolutions chat | its clone `AI Control Tower/.chats/evolutions`, branch `evolutions`; its claims file; its reports; new handover files | same |

A work chat that needs a shared file changed writes the request into its report and
stops that branch. The control room decides and writes it.

### Claims

`_tower/claims/control-tower.<chat>.yml`, one file per chat so two chats never write
the same file. Before touching a path a chat checks every claims file, and never
writes a path another chat holds. It releases the claim when the story is merged.

### Clones, not worktrees

Chosen for a verified reason: git 2.34 in the Claude VM writes worktree links as
absolute paths containing the creating session's id, so a worktree made in one chat is
broken in every other chat and on the Mac. Tested 2026-09-20. Each chat has a full
clone whose origin is the relative path `../..`, verified to fetch from any session.

### Merge, which is also the gate

Only what the control room merges into main is what launchd runs. A half-finished edit
in a work chat's clone can never run overnight. Until promote.sh exists at M1, the merge
is the nearest thing to a promote, and it is done in the control room, never by a work
chat.

### Orders

`_tower/bus/orders/control-tower/<chat>/O-NNNN.yml`, reports in
`_tower/bus/reports/control-tower/<chat>/`. One order in flight per chat. A report is
always written, including on failure.

### Autonomy, from the registry

Bugs at L1: fix, test, report, never promote, and no promote exists before M1. Evolutions
at L2: build inside an accepted design, stop before promote. Both still stop for: a design
not yet accepted, a claimed path, a shared file, a failing test, a needed derogation.
The M0 hold binds both: until S-004 passes, Evolutions writes designs and documents only.

## Closes when

The M1 audit confirms, for every governed project with work chats, that no shared file
was written by a work chat and no path was written under another chat's claim.
