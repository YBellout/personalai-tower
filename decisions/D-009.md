# D-009  Folder and git layout

    Scope:       global
    State:       answered
    Decided by:  Yassir, 2026-09-20
    Resolves:    D-001 option B
    Supersedes:  nothing

## Context

A non-technical operator has to be able to see which code is live without reading
git. Two visible folders beat a branch he cannot see, and the layout has to map onto
a container image later without being rebuilt.

## Options

1. **Recommended, and taken.** The repo lives in `dev/`. `prod/` is a plain copy
   written only by promote, tagged in git, never edited by hand, and maps one to one
   onto a container image when the mini exists.
   Addition carried with the pick: `prod/` sits outside git and so has no integrity
   check of its own, so promote must write a sha256 release manifest into `prod/`.
2. One repo covering both folders, `prod/` committed. Visible in Finder, and every
   promote doubles the repo and makes the diff useless.
3. Branches instead of folders, `main` and `prod`. Correct for a developer, invisible
   in Finder, and it breaks the constraint that git is never typed.

## Reversibility

Option 1 to option 3 is a day of work and no data loss, the folders become branches
and the launchers change. Option 1 to option 2 is one `git add`. The sha256 manifest
is additive and can be dropped without touching anything else.

The irreversible part is habit, not code: once `prod/` has been hand-edited once, the
guarantee that prod equals a tagged release is gone until the next promote.

## Cost of not deciding

promote.sh, rollback.sh, the policy file's write lists and the container mapping all
sit on this shape. None of them can be written, so M1 cannot start.
