# D-016  Two work streams: Operations and Evolutions

    Scope:       global
    State:       answered
    Decided by:  Yassir, 2026-09-20
    Supersedes:  nothing. Refines the object model (design doc, section 8): stories,
                 orders and releases keep their meaning, this names the two streams
                 they flow in.

## Context

Work on the Tower and on every governed project arrives in two unlike shapes that
were being planned, run and reported as one list: things that must run (batch jobs,
scheduled runs, the heartbeat, an audit, a promote) and things that change what the
project is (a bug to fix, a feature from a story). Mixing them hides which stream is
stalled, and lets an execution failure look like a backlog problem or the reverse.

## Options

1. **Recommended, and taken.** Two named streams, every unit of work belongs to
   exactly one. **Operations**: batch and execution runs, scheduled or on demand,
   that leave the code unchanged. **Evolutions**: bug fixes, and feature evolutions
   that come from stories, that leave the code changed. Reported separately in the
   status, planned separately in the evolution map, same for the Tower and for every
   governed project.
2. Three streams, splitting Evolutions into bugs and features. Finer, but bugs are
   small and stories already carry the size; a third column in every status is more
   than it buys today.
3. Status quo, one list. Rejected by the requirement itself.

## Reversibility

Fully reversible. It is a label on stories, orders and status rows, one heading in
each evolution map, and one section in `knowledge/status.md`. Option 2 remains
reachable later by splitting one heading.

## Cost of not deciding

The first project adopted at M1 would arrive with its own mix of runs and changes and
the Tower would have no rule for how to sort them, so each project would sort them its
own way, which is exactly what objective O3 forbids.

## The decision

### Rule 1, two streams, one home each

| Stream | Holds | Unit | Leaves the code | Lives in |
|---|---|---|---|---|
| Operations | batch runs, execution runs, scheduled jobs, audits, promotes, backups | an order (O) or a scheduled run | unchanged | `bus/orders/`, `bus/reports/`, `bus/events.log` |
| Evolutions | bug fixes, and feature evolutions from stories | a story (S) | changed | `evolution/<project>.md`, `docs/stories/` |

A unit that would sit in both is two units, one per stream, linked.

### Rule 2, applies everywhere

Binding on the Control Tower first, per `policy/self-governance.md`, and on every
governed project from adoption step 8, when its evolution map is created with the
two headings already in it.

### Rule 3, how it shows

- Every evolution map carries, under its current release, an `Evolutions` backlog
  (bugs and feature evolutions, each tagged `bug` or `feature`), and an `Operations`
  section listing the runs the project owns and their schedule.
- The status (D-015) reports the two streams as two rows in the Stories table's
  place at M1, when the UI renders it: one for Evolutions (stories open, in progress,
  blocked), one for Operations (last run, last result, next run). Until then the
  `heartbeat` block in `status.json` is the Operations row and the `stories` block is
  the Evolutions row. The json shape does not change today.

### First application

The Tower's own map, `evolution/control-tower.md`, gains the two headings in the same
commit as this file. Its Operations today: the heartbeat (every 30 minutes, launchd).
Its Evolutions today: S-013, the raw-note intake UI, tagged `feature`, plus the
heartbeat lock-file fix named in the 18:20 handover, tagged `bug`, once it is a story.

## Closes when

The audit at M1 confirms every governed project's evolution map has both headings and
every open unit of work sits under exactly one of them.
